# LingBot-World 2.0：15 秒离线 batch 推理实测

## 结论

- 最高实测节点吞吐是 **4 个 2-GPU 服务并行**：287.07 条视频/小时，35.88 条/GPU·小时；单条落盘延迟 p50 为 50.05 秒。
- 更稳妥的生产默认是 **2 个 4-GPU 服务并行**：262.97 条/小时，p50 27.17 秒。它只比最高吞吐低 9.2%，但推理中采样显存约 63,227 MiB/卡，而 4x2 已达到约 79,513 MiB/卡。
- 1 个 8-GPU 服务的单条延迟最低（p50 17.98 秒），但节点吞吐只有 200.01 条/小时。
- 8 个 1-GPU 服务都能启动，但并发预热时 OOM；单进程已用 79.12 GiB，只剩 54.12 MiB，再申请 366 MiB 失败。因此当前参数下不能用 1-GPU 副本做稳定生产。
- 本轮“第三人称”请求与第一人称请求共用了官方第一人称 conditioning frame。视频 QA 显示输出仍是第一人称视角，所以性能数字有效，但第三人称标签不能作为视觉质量结论。真实数据合成必须提供独立的第三人称首帧。

## 实测结果

| 拓扑 | 并发视频数 | 结果 | 单条延迟 p50 / p95 | 节点吞吐 | GPU 效率 | 聚合实时因子 | 推理中显存采样 |
|---|---:|---|---:|---:|---:|---:|---:|
| 1x8 GPU | 1 | 8/8 成功 | 17.98 / 18.29 秒 | 200.01 条/小时 | 25.00 条/GPU·小时 | 0.847x | 约 60,924 MiB/卡 |
| 2x4 GPU | 2 | 8/8 成功 | 27.17 / 27.66 秒 | 262.97 条/小时 | 32.87 条/GPU·小时 | 1.113x | 约 63,227 MiB/卡 |
| 4x2 GPU | 4 | 8/8 成功 | 50.05 / 50.27 秒 | **287.07 条/小时** | **35.88 条/GPU·小时** | **1.215x** | 约 79,513 MiB/卡 |
| 8x1 GPU | 8 | 预热 OOM | 无 | 无 | 无 | 无 | 进程 79.12 GiB，仅余 54.12 MiB |

相对 1x8，2x4 的节点吞吐提升 31.5%，4x2 提升 43.5%。4x2 相对 2x4 只再提升 9.2%，但延迟从 27.17 秒上升到 50.05 秒，并显著压缩显存余量。

“聚合实时因子”是生成的视频总时长除以墙钟时间。例如 4x2 的 1.215x 表示一小时墙钟时间可产出约 72.9 分钟视频内容。节点吞吐与单条延迟不同：4x2 每条更慢，但四条并发，所以总产量最高。

## 测试口径

- AWS EKS `us-east-2`，`p5.48xlarge` Spot，8x H100 80GB。
- SGLang 代码 `d9a7e0e6630ea8aea135191115a13e6451618a6f`。
- 镜像 `lmsysorg/sglang:dev@sha256:8f78575e03ab59a39191a4a6f718bbbe1726fa940f72a86a187a3f1628ada9a7`。
- 模型 `robbyant/lingbot-world-v2-14b-causal-fast-diffusers`，revision `59cccf49f2d2dd27418ae7a04b82b10868d455c2`，BF16，4 个 DMD step。
- 832x480、25 FPS、381 帧，即 15.24 秒；关闭上采样和插帧。
- 每个成功拓扑 8 条视频，4 个第一人称 prompt、4 个第三人称 prompt，使用不同 seed/action。
- WebSocket 返回 raw RGB，客户端同步编码为 H.264 MP4；延迟统计到 MP4 落盘并通过帧数校验为止。
- 每个服务先生成 3 个 chunk 预热；预热时间与稳态测量分开。
- 服务内部 `batching_max_size=1`，所以离线并发通过多个独立服务副本实现，而不是在一个服务内堆 request batch。

本地 OpenCV 二次校验了 1x8 的 8 个 MP4：每个都是 381 帧、832x480、25 FPS、15.24 秒。原始 JSON 见 `comparison.json` 和各拓扑的 `summary.json`。

## 视觉 QA 与第一/第三人称边界

第一人称和“第三人称”接触表都显示了手臂/载具的第一人称构图。第三人称 prompt 没有覆盖 conditioning frame 中的视角，因此后续生产配置应分别传：

- `--first-frame-first-person <egocentric-frame>`
- `--first-frame-third-person <third-person-frame>`

基准脚本现在会在两类请求共用 conditioning frame 时打印警告。由于图像内容不会改变模型张量形状，本轮吞吐仍可用于容量规划；它不能用于判断第三人称生成质量或合格率。

## 部署建议

1. 默认使用 2x4 GPU：两条独立服务、前置任务队列轮询分发。它在吞吐、单条等待时间和显存余量之间最平衡。
2. 只追求最大离线产量时使用 4x2 GPU，但应保持当前分辨率、4 steps、无上采样/插帧，并设置显存/OOM 监控；不要在每个 2-GPU 服务内再并发第二条。
3. 不使用 8x1 GPU；若必须单卡，需要量化、CPU/offload、降低分辨率或更短上下文，并重新做完整性能与质量验证。
4. 大规模上线前再跑至少 100 条、使用真实一/三人称首帧分布，并把对象存储上传时间、重试率和视觉合格率纳入端到端指标。

## 部署过程中的两个实证问题

- B200 Spot 新实例实时返回 `UnfulfillableCapacity`，所以本报告只声明 H100 结果。
- 多服务若不显式设置不同的 `--master-port`，并发启动会因默认端口竞态出现 `EADDRINUSE` 和 NCCL rank 串线。可复现脚本已为每个服务分配独立 master port。
- 2x4 与 4x2 的完整 `summary.json` 在节点终止前已复制并包含逐条 ffprobe 校验结果，但这两组的 MP4/服务日志未保留；1x8 的 8 个 MP4、服务日志和 GPU telemetry 均已保留。本地 OpenCV 又对这 8 个 MP4 做了独立帧数/时长校验。
- 本任务的 H100/B200 Pod 与 ConfigMap 已全部删除。最后一台 H100 NodeClaim 属于共享 Karpenter 节点池，节点上仍有一个非本任务的、状态为 `Succeeded` 的 `ray/lwdp-ray-head-log-cleanup-*` Job Pod，Karpenter 因此报告 `Unconsolidatable: non-empty consolidation disabled`；未越权删除该 Job 或共享 NodeClaim。
