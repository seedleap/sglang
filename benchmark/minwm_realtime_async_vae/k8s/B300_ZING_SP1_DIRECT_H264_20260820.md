# B300 Zing SP=1 Direct H.264 Deployment, 2026-08-20

This note records the isolated aws03 B300 deployment that was validated on
2026-08-20 for a Zing-only realtime WebUI. It is intentionally separate from
the older `aws03-west2-haoze-20260813.yaml` dual-model capacity-block record.

## Scope

- Cluster/account: aws03, us-west-2.
- Namespace: `minwm-zing-b300-sp1-20260819`.
- Public WebUI: `https://zing-b300-world-studio.loopit.me/`.
- Model: Zing
  `wan22-5b-stage3-dmd-47-0808-2fb2cfec2a2/gs3200-ema-student-v1`.
- User-facing mode: WebSocket + direct H.264 from the VAE path.
- Resolution/FPS: 1280x704, 24 FPS.
- Session lifetime: 70 seconds.
- GPU layout on one B300 host:
  - 7 denoiser workers, one GPU each, `sp-degree=1`.
  - 1 async TAEHV VAE worker, one GPU.
  - Coordinator, gateway, and WebUI CPU pods on the same isolated node.

This topology is for isolated benchmarking and human evaluation. It must not
share node selectors, taints, services, or public DNS with `open-world` or any
other production chain.

## Runtime topology

```text
Browser
  -> WebUI public NLB / TLS
  -> WebUI pod
  -> Gateway x2
  -> Coordinator x1, memory backend
  -> Zing denoiser StatefulSet x7, SP=1
  -> Zing async TAEHV VAE x1
  -> Gateway
  -> Browser over WebSocket H.264
```

The VAE exposes the service name `zing-vae-probe` and the denoisers call:

```text
ws://zing-vae-probe:18081/v1/realtime_vae/decode
```

The gateway smoke path must emit `media_init` and `media_payload` messages, not
legacy `frame_batch` payloads, when H.264 is active.

```text
requests: cpu=8,  memory=96Gi,  ephemeral-storage=8Gi,  nvidia.com/gpu=1
```

The tested CPU/memory increase removes CPU throttling as a first-order
denoiser bottleneck. If performance still drops after startup, inspect
denoiser stage timings and GPU clocks before increasing these limits again.

## Realtime startup warmup gate

Do not rely on `/health` alone. `/health` only proves that the process is
listening; it does not prove that a 720p realtime chunk has initialized CUDA
graphs, packed attention metadata, image/text conditioning, and remote VAE
decode paths.

The denoiser container now creates a shared ready file only after completing two
one-chunk realtime sessions:

```text
/worker-epoch/zing-720p-ready
```

Warmup request shape:

```text
generation_mode=i2v
size=1280x704
fps=24
num_inference_steps=4
guidance_scale=1.0
max_chunks=1
realtime_output_format=jpeg
realtime_preview_max_width=1280
realtime_output_pacing=false
output_compression=90
realtime_causal_sink_size=8
realtime_causal_kv_cache_num_frames=32
```

The warmup waits for websocket close code `1000` with reason
`generation complete`. Waiting only for the first payload can leave an active
startup session behind and make the coordinator report less capacity than
expected.

The heartbeat init container must block on the same ready file before it starts:

```sh
READY_FILE=/worker-epoch/zing-720p-ready
until [ -f "${READY_FILE}" ]; do sleep 1; done
exec python3 -m sglang.multimodal_gen.runtime.entrypoints.realtime_worker_heartbeat ...
```

Readiness and startup probes should also require the ready file:

```sh
test -f /worker-epoch/zing-720p-ready &&
  curl --fail --silent --max-time 2 http://127.0.0.1:30000/health >/dev/null
```

This keeps cold or partially warmed workers out of coordinator capacity during
rolling updates.

## Rollout procedure

Use rolling updates with `partition=0` only after the template contains the
ready-file warmup gate:

```sh
kubectl --kubeconfig /tmp/codex-aws03-kubeconfig-b300 \
  -n minwm-zing-b300-sp1-20260819 \
  patch sts zing-denoiser --type merge \
  -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"partition":0}}}}'

kubectl --kubeconfig /tmp/codex-aws03-kubeconfig-b300 \
  -n minwm-zing-b300-sp1-20260819 \
  rollout status sts/zing-denoiser
```

During rollout, expect one denoiser ordinal at a time to be unavailable. The
coordinator should keep advertising the already warmed workers. A temporary
capacity drop is acceptable; registering cold workers is not.

## Known pitfalls

- Whole-DiT `--enable-torch-compile` was not kept for this B300 SP=1 chain. In
  this deployment it produced very long startup compile time and could leave
  stale startup sessions; keep `--enable-torch-compile false` unless a separate
  canary proves stable 720p realtime latency.
- Built-in generic startup warmup is not enough when its shape differs from the
  production session shape. Warm exactly `1280x704`, 24 FPS, sink 8, window 32.
- `--realtime-session-idle-timeout-s 60` is too tight for cold B300 realtime
  warmup. Use 180 seconds for internal startup sessions, while keeping
  user-facing `--realtime-session-max-lifetime-s 70`.
- The heartbeat must wait on the ready file, not only `/health`, or the
  coordinator can route users to cold workers.
- A successful direct worker warmup is not proof of direct H.264; use gateway
  smoke and check for `media_init`/`media_payload`.
- Keep this namespace and DNS isolated. Do not reuse `open-world` services,
  taints, load balancers, or public hostnames for this lab.
